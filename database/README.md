# ElevateMe — Canonical Database (`database/`)

Revamp-managed Flyway schema. Postgres 14 compatible.

## Read-only reference: `supabase/`

`supabase/migrations/001_core.sql`, `002_participation.sql`, `004_logic.sql`
(plus `003_rls.sql`, `005_scoring_rework.sql`, `006_*`, `007_*`, `008_*`, `seed.sql`)
are the **legacy Supabase backend**. Do not edit, do not migrate from them
automatically, do not drop their `public.*` tables.

Preserved semantics from the legacy schema:

| Legacy (`public.*`) | Canonical (`app.*`) | Notes |
|---|---|---|
| `profiles.id = auth.users.id`, no FK to `auth.users`, adopt-by-email | `profiles.supabase_subject UUID UNIQUE NULL` | Opaque link only, never `REFERENCES auth.users`. Java owns identity. |
| `elevate_me_seq START 131`, `EM-` + 5 digits, never reused | `app.elevate_me_seq START 131` | `nextval()` consumed only when an ID is actually assigned. |
| `registrations UNIQUE(student,program,session)` NULL bug documented in `002` | Two partial unique indexes | Fixes `NULL != NULL` so duplicate program-level rows are rejected. |
| `programs.registered` counter via trigger | `registered_count` cache + `FOR UPDATE` pattern | Capacity enforced transactionally in Java, not by a DB hard cap. |
| 10 criteria × 0–100, total/1000, final/10 (`005`) | `rubric_criteria` 10 stable keys, `evaluation_scores.score INT 0–100` | Bounds stay in the DB; completeness stays in Java (see V3 note). |
| `audit_log` append-only | `audit_events` append-only trigger | Safe `before/after JSON`, `request_id`. |

Flyway defaults: `locations=filesystem:database/migrations`,
`table=flyway_schema_history`, applied in `V1..V12` version order
(`V5` then `V5.1` then `V6` — Flyway parses `V5_1` as version `5.1`).
Each migration is one transaction, re-runnable guards (`IF NOT EXISTS` /
`ON CONFLICT DO NOTHING` / `DROP TRIGGER IF EXISTS`) where Postgres allows it.

## Global conventions

- **UUID PKs.** Every entity table: `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`.
  Requires `CREATE EXTENSION IF NOT EXISTS "pgcrypto"`. No serial IDs except
  `audit_events.id BIGINT GENERATED BY DEFAULT AS IDENTITY` (ordering only).
- **UTC time.** All timestamps `timestamptz NOT NULL DEFAULT now()`
  (`starts_at/ends_at`, `confirmed_at`, `released_at`, `expires_at`, …).
  Never `timestamp without time zone`, never client-local strings.
  Ranges always `CHECK (ends_at IS NULL OR ends_at >= starts_at)`.
- **Optimistic locking.** Every mutable entity has
  `row_version INTEGER NOT NULL DEFAULT 1`. Java increments with
  `UPDATE … SET row_version = row_version + 1 WHERE id = ? AND row_version = ?`
  and treats `rowcount = 0` as a conflict. Migrations never reset it.
- **Soft-archive, never hard delete.** Mutable tables carry
  `archived_at TIMESTAMPTZ NULL`. “Delete” = `SET archived_at = now()`.
  Unique constraints that must allow re-creation after archive are partial:
  `… WHERE archived_at IS NULL`. History tables (revisions, scores, audit,
  outbox) have no `archived_at` — they are immutable.
- **`updated_at` maintenance.** `app.touch_updated_at()` trigger sets
  `NEW.updated_at = now()` + `NEW.row_version = OLD.row_version + 1`
  on user `UPDATE`. Seed/migration bulk loads bypass it explicitly if needed.
- **FK discipline.** `ON DELETE CASCADE` only for strict owned children
  (scores → revision, messages → thread, recipients → recommendation).
  References to `profiles` are `ON DELETE RESTRICT` / `SET NULL` so a user
  is never cascade-deleted. No FK ever points at `auth.users`.

## Roles: migration owner vs runtime

Do NOT invent production credentials. Create roles without passwords/logins
here; the deploy pipeline attaches secrets.

```sql
-- owner (runs Flyway, owns schema + tables)
-- GRANT ALL ON SCHEMA app TO elevateme_owner; ALTER TABLE … OWNER TO elevateme_owner;
-- runtime (used by the Java datasource ONLY)
-- GRANT USAGE ON SCHEMA app TO elevateme_app;
-- GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO elevateme_app;
-- GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA app TO elevateme_app;
-- ALTER DEFAULT PRIVILEGES … GRANT … TO elevateme_app;
```

- `elevateme_owner`: DDL + migrations. Only CI/migration job assumes it.
- `elevateme_app`: DML only, no `CREATE/ALTER/DROP`, no `TRUNCATE`
  (revoked), no direct `nextval` abuse beyond the ElevateMe-ID function,
  no `SECURITY DEFINER` functions except the whitelisted ID allocator.
- `REVOKE ALL ON SCHEMA app FROM PUBLIC` in V1. No table grants to
  `PUBLIC`, `anon`, or `authenticated` — those are legacy Supabase roles.

## Private schema / deny-by-default RLS (Java-only access goal)

- All canonical tables live in the private `app` schema, never `public`.
- Every `app.*` table has `ENABLE ROW LEVEL SECURITY` with **zero permissive
  policies** (deny by default). The Java service connects as `elevateme_app`
  via a private network and is granted table privileges directly; RLS stays
  deny-all so any future Supabase/PostgREST exposure returns zero rows unless
  an explicit policy is added and reviewed.
- There is intentionally no `USING (true)` / `FOR ALL TO authenticated`
  policy anywhere in `database/`. If direct client access is ever required,
  add a narrow, reviewed policy per table — never a blanket one.
- Defence in depth: `REVOKE … FROM PUBLIC, anon, authenticated` is repeated
  in each migration so a half-applied chain cannot leak.

## Transactional notes (Java must follow)

- **ElevateMe ID** (`EM-#####`): `nextval('app.elevate_me_seq')` fires only
  inside `app.assign_elevate_me_id()` when a `student` row with
  `elevate_me_id IS NULL` is inserted (or transitions to `Approved`).
  Numbers are never reused; failed transactions roll the consumption back
  only to the extent Postgres sequences allow (gaps are fine, reuse is not).
- **Capacity**: `SELECT … FROM app.programs WHERE id = ? FOR UPDATE`,
  then `COUNT(*) Confirmed`, then `INSERT/UPDATE registration`. The
  `refresh_program_registered_count()` trigger keeps the counter honest.
- **Score completeness** (“no NULL on submitted”): Postgres cannot declare
  “revision is complete” without a trigger on a variable-size set, so V3
  stores every score as non-null `INT 0–100` and Java rejects
  `DRAFT → SUBMITTED` unless all 10 criteria for the active rubric version
  are present. A documented partial-check alternative is included as a comment.
- **Pin max 3**: `recommendation_recipients.pinned_order 1–3`, at most 3
  pinned rows per student enforced in Java (count query in the same txn).
- **Idempotency**: `report_releases UNIQUE(actor_id, idempotency_key)`,
  `outbox_events.dedupe_key UNIQUE`. Retries send the same key.

## How to run

```bash
# fresh local DB (Postgres 14)
createdb elevateme
flyway -url=jdbc:postgresql://localhost:5432/elevateme \
       -user=elevateme_owner \
       -locations=filesystem:database/migrations migrate

# dev demo data (NEVER production)
psql $DATABASE_URL -f database/seed_dev.sql
```
